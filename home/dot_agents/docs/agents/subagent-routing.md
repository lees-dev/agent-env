## Subagent routing (owner, 2026-11-06)

Applies to every agent harness: Claude Code, Codex, Grok, Muse Code and any other.

- **If `delegate_task` started you, do your assigned job yourself.** Do not start agents, panels or councils unless your brief says to. The rules below are for the main thread.
- **The main thread orchestrates; Opus builds.** New T3 threads start on GPT Sol at medium effort. The main thread plans, routes, judges findings and makes the final call. Code for a scoped change (feature, fix, refactor, hard bug, conflict resolution, review fixes) is written by Opus (`claude-opus-5-5`, high; xhigh for hard bugs): if you are not Opus, delegate it to Opus. You may make a small fix yourself: up to about 20 changed lines in one or two files, with no new behavior.
- **Councils are for unresolved design trade-offs.** Convene the planning council (Opus 5.5, GPT Sol, Muse Wonder Full and Grok 4.7, all at high effort, in parallel and read-only) only when the user asks for one, or when your own investigation leaves viable approaches whose trade-offs the evidence does not settle. A request to plan, a new feature, a migration or a spec does not by itself call one: when the approach is settled, the main thread writes the plan. Members research and propose independently; the main thread synthesizes, says who proposed what, and returns the plan.
- **Reviews.** By default a change gets one focused cross-family review: GPT Sol (high) for Opus-built work, Opus for GPT-built work, GPT Sol otherwise, plus a second family for security, auth, data loss, migrations or concurrency. Routine fixes stay on that one reviewer whatever their line or file count. The review panel (GPT Sol high, Muse Wonder Full xhigh, Grok 4.7 high and Sonnet 5.5 high, read-only, in parallel) is for Opus-built complex new behavior or a sensitive path (security, auth, data, migrations, concurrency, CI). Gemini is not used; Grok takes its seat.
- **Muse runs on its Contributor variants.** Target each Muse model's `-contributor` ID (`muse-wonder-full-1.0-contributor`, `muse-wonder-1.0-contributor`, `muse-spark-1.3-contributor`) at the routed effort. Use a regular Muse ID only when the user names it or the live model list lacks the variant.
- **Route every agent you start.** Before spawning any subagent, delegate, reviewer, council member or second opinion, load the `subagent-routing` skill (`~/.agents/skills/subagent-routing/SKILL.md`, also `~/.claude/skills/subagent-routing`). It maps each task type to a model family, model ID and effort level, always set explicitly. An unrouted agent inherits your own model, which is the failure this rule stops.
- **In T3 Code, start every agent with `delegate_task`** (builder, reviewer, researcher, council member, background agent), whatever the target's family, including your own: no Claude `Agent`/`Workflow`/`Task`, Codex `spawn_agent`, or `claude -p`/`codex exec`/`grok -p`/`muse exec`. Set `target.providerInstanceId`, `target.model`, effort in `target.options` and a `role`. Each delegate shows up as its own T3 thread with its model. `delegate_task` only starts children in the starting thread's own project (builders get `isolation: "worktree"`). For work in another repo, start the builder or reviewer with `t3_thread_launch` in that repo's T3 project: `workspaceStrategy: {type: "worktree", branch, baseRef}`, `modelSelection` set (Opus, high effort, for builders), the brief in `message`; then `t3_thread_wait` / `t3_thread_read`, never a poll loop. That is an allowed exception to "new top-level thread only when the user asks". Phased work in another repo uses `t3_thread_launch` the same way. A launched thread's brief opens with "You are a builder/reviewer launched for this task: do the job yourself and start no agents or threads"; stop such a thread with `t3_thread_interrupt` (not `task_cancel`); the parent keeps responsibility for its reviews. The repo's lander (the `land-queue` schedule) runs on Claude Sonnet `claude-sonnet-5-5`, medium effort. See the T3-first rules. Outside T3: your own family through your native tool with the model set; another family through its harness CLI.
- **Reviews cross families.** At least one reviewer's model family differs from the builder's, unless a skill the user named (`council`, `sol-loop`, `how`) sets its own reviewers or models.
