## T3-first (owner, 2026-11-06)

Applies to every agent harness running inside T3 Code: Claude Code, Codex, Grok, Muse Code and any other. You are inside T3 when T3's tools (`delegate_task`, `t3_*`, `link_pull_request`, `preview_*`, `html_render` and the rest) are listed. T3 MCP tools may be deferred: load them (ToolSearch or your harness's equivalent) before deciding one is missing. Not every harness gets every T3 tool (for example `t3_background_wait` is Claude-only); use the ones you have.

- **Use T3's own tool whenever one does the job.** Fall back to another tool only when T3 has none, your harness does not list it, it fails (say so), or you are outside T3.
- **This rule wins.** It overrides any skill, plugin, doc or default that names another mechanism. That includes third-party skills (mattpocock/skills, plugin skills), system reminders that suggest a Workflow, and T3's own default advice to use native subagent tools for children on your own provider. When a skill says "start a subagent", "run in the background", "spawn reviewers", "use a worktree" or "poll until", carry out that step with the T3 tool below. Outside T3, follow the skill as written.
- **If `delegate_task` started you**, do your assigned job yourself; do not start agents, panels or councils unless your brief says to.

| Job | Use in T3 | Instead of |
| --- | --- | --- |
| Any agent you start in this thread's project: builder, reviewer, researcher, council member, second opinion, background agent | `delegate_task` (model, effort and `role` set by `subagent-routing`; `isolation: "worktree"` for builders). `task_cancel` stops one. Follow its `next`; do not poll | Claude `Agent`/`Workflow`/`Task`, Codex `spawn_agent`, `claude -p`, `codex exec`, `grok -p`, `muse exec` |
| A builder or reviewer for work in another repo (another T3 project) | `delegate_task` only starts children in this thread's own project. Use `t3_thread_launch` with that repo's `projectId`, `workspaceStrategy: {type: "worktree", branch, baseRef}`, `modelSelection` set by `subagent-routing` (Opus, high effort, for builders) and the brief in `message` (opening with "You are a builder/reviewer launched for this task: do the job yourself and start no agents or threads"); then `t3_thread_wait` / `t3_thread_read` (on a `t3_thread_wait` timeout with `next`, end the turn; never poll in a loop). `t3_thread_interrupt` stops one (not `task_cancel`). This is an allowed exception to "new top-level thread only when the user asks" | `delegate_task` in the wrong project, cloning the other repo into this one, `claude -p` / `codex exec` |
| A separate checkout for parallel or PR work | `delegate_task` with `isolation: "worktree"` (a new checkout of the parent commit; fetch and check out a PR head inside it when needed); `t3_thread_launch` with `workspaceStrategy` (can name `baseRef` and `branch`); `t3_worktree_handoff` to move this thread; `t3_worktree_list` / `t3_worktree_status` to inspect | `git worktree add` by hand in your local checkout, `~/wt-*` folders, `EnterWorktree` |
| A new top-level thread (only when the user asks for one, for work in another repo as above, or for an issue thread in an issue batch) or handing work to a fresh thread | `t3_thread_launch` / `create_threads`; `t3_thread_read`, `t3_thread_search`, `t3_thread_wait`, `t3_thread_send` for existing threads | a background agent, a new terminal session |
| Waiting for a delegate | follow its `next`; T3 wakes you | `task_status` polling, `sleep`, `Monitor`, `ScheduleWakeup` |
| Waiting for a background shell command or build you started | Claude Code: `t3_background_wait` with its task ID. Other harnesses: your harness's own wait for that command (for example a foreground shell call with a timeout) | `sleep` loops, `Monitor`, `ScheduleWakeup` |
| A PR you open, take over or push to | `link_pull_request` / `link_pull_requests` right after. Watch only when something outside your control still blocks the merge (a human review, required checks on a repo that still has CI): `watch_pull_request`, end the turn, `unwatch_pull_request` before handing back. A delegated child never watches. A PR that `land-pr` reports `MERGED` needs no watch; a `QUEUED` / `QUEUE-FULL` one is watched only by a main thread that must see it merge (`full-send`, or `babysit-pr` asked to land). `write_pull_request_guides` / `read_pull_request_guide` for review tours | `gh pr checks --watch`, sleep-and-poll loops |
| Following a non-PR GitHub run (release, deploy) | run `gh run watch` as a background command and wait for it as in the background-shell row (Claude Code `t3_background_wait`; other harnesses their own wait); `watch_pull_request` is only for PRs | polling `gh run view` in a loop |
| Scheduled or recurring agent work | `schedule_task`, `list_scheduled_tasks`, `run_scheduled_task_now`, `delete_scheduled_task` | cron, Windows Task Scheduler, `CronCreate`, `/loop`. Plain scripts that need no agent may stay on the OS scheduler |
| Landing a PR | `land-pr <n> --sha <gated sha>` (rules in `pr-workflow` section 4); each repo's lander is a T3 `schedule_task` named `land-queue`, kicked with `run_scheduled_task_now` on `QUEUED` / `QUEUE-FULL`. Merging by hand with `gh pr merge` is allowed only under that section's fallback (no `land-pr`, or no lander schedule yet; and all its preconditions hold) | `gh pr merge` outside the fallback, `--auto`, GitHub's merge queue, cron |
| A repo credential | `.env.op` references, injected into `.env.local` by `agent-worktree setup` or run with `op run --env-file .env.op --`; store a new one the same turn with `agent-secret put` (see the credentials rules) | values in committed or copied `.env` files, chat, argv |
| A secret, key or token only a human has | `request_secret`, then pass its `secretRef` (or `delivery: "file"` for a shell command); store it with `agent-secret put` when a repo needs it again | asking in chat, reading it from a file you were not given |
| Showing a chart, diagram, mockup or table here | `html_preview` then `html_render` | an artifact or local server just to show it |
| Browser work on a web page or dev server: open, drive, check, screenshot, record | `preview_open` (with `target` for a dev-server port), `preview_act`, `preview_snapshot`, `preview_wait_for`, `preview_recording_*`; close tabs you opened | Playwright MCP or Chrome DevTools MCP for driving pages, a separate browser (see Exceptions) |
| iOS Simulator or Android Emulator | `device_list`, `device_open` (then its `agent-device` command), `device_screenshot`, `device_close` | `xcrun simctl`, `adb`, `idb` for driving the device |
| Cloning or registering a project | `t3_project_clone` then `t3_project_create` (then `repo-defaults` per the repo-defaults rules); `t3_project_list` / `t3_project_read` | plain `git clone` into a random folder |
| Another of your machines | `t3_environment_links`, then pass its `environmentId` to the T3 tool; `t3_environment_link` with a `hint` to link a new one | `ssh` for T3 actions (ssh stays fine for builds, logs and sync scripts) |
| Files for another thread, queued messages, pending questions | `t3_attachment_prepare_upload` / `t3_thread_send_attachments`, `t3_queue`, `t3_pending_request` | pasting content into chat |

Things T3 has no tool for stay as they are: landing a PR (`land-pr`, or the `gh pr merge` fallback, per `pr-workflow` section 4), git commits and pushes, builds and tests, Linear, plain OS scripts, and WSL or server clones and worktrees used for CodeRabbit or proof runs (`cr/*`, `prove/*`).

**Carrying out third-party skills in T3.** These skills start agents, threads or worktrees their own way; do those steps with T3 tools: mattpocock `implement-spec`, `code-review`, `research`, `wayfinder`, `chief-of-staff`, `improve-codebase-architecture`, `codebase-design` (design it twice), `grilling`, `claude-handoff`; plugin `code-review`, `feature-dev`, `skill-creator`, `commit-commands` (`clean_gone`, `commit-push-pr`).

- `delegate_task` children run asynchronously. Start them in one turn, follow `next`, combine results when they arrive, never poll. This holds where a skill says "in the foreground" or "don't block".
- A named agent type (`code-explorer`, `code-architect`, `code-reviewer`, a haiku/sonnet "agent") becomes a `delegate_task` whose brief is that agent's prompt. In third-party skills, model and effort come from `subagent-routing`, not from model names in the skill. The owner's own skills (`how`, `council`, `sol-loop`) set their own models.
- `implement-spec`: each implementer works in its own `isolation: "worktree"` checkout on its own branch; the merger creates or updates the integration branch in the main checkout from those branches; clean up per `pr-workflow` §7 with `t3_worktree_list`.
- `/claude-handoff` counts as the user asking for a new thread: `t3_thread_launch` with the summary file as the prompt, not `claude --bg`. `/handoff` only writes the file.
- Before removing any worktree (`clean_gone`, cleanup), check it with `t3_worktree_list` / `t3_worktree_status`; never force-remove one a T3 thread still uses, or one whose PR carries a queue label (`queued`, `landing`, `queue-blocked`, `queue-hold`, `queue-waiting`).
- After `commit-push-pr` or any other `gh pr create`, call `link_pull_request`.

**Exceptions** (keep the other tool):

- Chrome DevTools MCP for what the preview tools cannot do: Lighthouse, performance traces, heap snapshots, isolated cookie contexts. A project's own Playwright/Cypress test suite runs through its test runner. Electron and other desktop apps keep their own harness or CDP debug port.
- `claude -p` / `codex exec` inside scripts that use them as a measurement harness (for example `skill-creator`'s trigger tests), not as a subagent.
- Human-run scripts that collect secrets in the user's own terminal (`wizard`). `request_secret` is for secrets the agent itself needs.
- The user explicitly names another tool (for example Herdr, or a Workflow). In Claude Code the hook that blocks `Agent`/`Workflow`/`Task` inside T3 is lifted for a session started with `T3_FIRST_OFF=1`.
